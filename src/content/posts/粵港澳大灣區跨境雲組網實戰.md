# 粵港澳大灣區跨境雲組網實戰：澳門 + 珠海雙 IDC 通過 CEN 打通阿里雲雙 Region

> 系列：澳門企業上雲實戰 · 第 1 篇
> 關鍵詞：阿里雲、CEN、Transit Router、VPN 網關、跨境帶寬包、大灣區、數據合規

## 一、為什麼要寫這篇

在大灣區做雲架構，最容易踩坑的從來不是「單地部署」，而是**跨境組網**。

最近幫一個客戶落地了一套典型架構：客戶在**澳門**和**珠海**各有一個自建數據中心（IDC），業務上需要兩地數據互通，同時又希望把一部分計算、存儲、分析能力放到阿里雲上就近落地。最終形成的拓撲是：

- 澳門本地 IDC ── IPsec VPN ──> 阿里雲 **cn-hongkong**（香港）Region VPC
- 珠海本地 IDC ── IPsec VPN ──> 阿里雲 **cn-shenzhen**（深圳）Region VPC
- 兩個 VPC 之間 ── **CEN（雲企業網）Transit Router + 跨境帶寬包** ── 打通

這套架構的技術細節在內地雲文章裡很少見，因為它踩中了一個純內地組網遇不到的環節——**跨境帶寬包與跨境合規**。這篇文章就把完整的設計思路、實施步驟、合規要點和實測避坑一次講清楚。

## 二、業務背景與訴求

客戶是典型的「一司兩地」佈局：總部與部分核心系統在澳門，生產/研發在珠海。訴求可以歸納為四點：

1. **兩地 IDC 需要互訪**：澳門的業務系統要能訪問珠海的數據庫，反之亦然。
2. **雲上就近計算**：澳門側的雲資源（RDS、大模型推理、數據分析）落在 cn-hongkong；珠海側落在 cn-shenzhen，各自就近、延遲最低。
3. **合規隔離**：澳門受《個人資料保護法》(PDPA) 約束，內地受《數據出境安全評估辦法》約束，哪些數據可以跨境流動必須可控、可審計。
4. **高可用與可觀測**：跨境鏈路是整條路徑最脆弱的一環，需要主備切換與流量監控。

為什麼不讓兩個 IDC 直接拉專線互聯、而要繞一圈雲？因為客戶的增量業務（數據中台、AI 推理）本來就在雲上，繞雲不僅順路，還能用 CEN 把「兩地 IDC + 兩地雲」編排成一張統一的網，未來掛新 Region（例如新加坡）只是加一個 TR 連接的事。

## 三、總體架構

![跨境組網架構圖](/images/gba-crossborder-architecture.png)

> 配圖說明：上圖為最終配圖（2080×1240）；同目錄另提供向量版 `/images/gba-crossborder-architecture.svg`，需要無損縮放或二次編輯時可直接引用。

拓撲說明：

```
┌───────────────┐        IPsec VPN        ┌──────────────────────┐
│  澳門本地 IDC  │ ───────────────────────>│  cn-hongkong VPC      │
│ 10.10.0.0/16  │                         │  172.16.0.0/16        │
└───────────────┘                         └──────────┬───────────┘
                                                      │
                                              CEN Transit Router
                                              + 跨境帶寬包(內地↔港澳)
                                                      │
┌───────────────┐        IPsec VPN        ┌──────────┴───────────┐
│  珠海本地 IDC  │ ───────────────────────>│  cn-shenzhen VPC      │
│ 10.20.0.0/16  │                         │  172.17.0.0/16        │
└───────────────┘                         └──────────────────────┘
```

三個關鍵組件：

- **VPN 網關（IPsec）**：每地 IDC 到對應 Region VPC 各建一條（或主備兩條）IPsec 隧道，承載 IDC ↔ 雲的流量。
- **CEN 企業版 + Transit Router（TR）**：把兩個 VPC 掛載到 CEN，TR 作為中心路由樞紐做跨 VPC 轉發。
- **跨境帶寬包**：內地（cn-shenzhen）↔ 港澳（cn-hongkong）屬於「跨境」互聯，必須單獨購買跨境帶寬包並綁定到 CEN，且需要相應的跨境資質。這是整套架構的合規與計費核心。

### 網段規劃：最容易翻車的第一步

四段地址**絕不能重疊**，這是跨境組網最常見的事故來源：

| 位置 | CIDR | 說明 |
|------|------|------|
| 澳門 IDC | 10.10.0.0/16 | 客戶既有內網段 |
| 珠海 IDC | 10.20.0.0/16 | 客戶既有內網段 |
| cn-hongkong VPC | 172.16.0.0/16 | 雲上新建 |
| cn-shenzhen VPC | 172.17.0.0/16 | 雲上新建 |

若客戶既有 IDC 網段已經衝突（很常見，兩地都用 192.168.0.0/16），要提前規劃 NAT 或重新劃分，不要等到 CEN 路由黑洞了才發現。

## 四、分步實施

### 步驟 1：兩地 VPC 與交換機

在 cn-hongkong 與 cn-shenzhen 各建一個 VPC，每個 VPC 至少跨兩個可用區建交換機（VSwitch），為後續多可用區高可用留餘地。

Terraform 片段（以 cn-hongkong 為例）：

```hcl
resource "alicloud_vpc" "hk" {
  provider   = alicloud.hk
  vpc_name   = "vpc-hk-macau"
  cidr_block = "172.16.0.0/16"
}

resource "alicloud_vswitch" "hk_a" {
  provider     = alicloud.hk
  vpc_id       = alicloud_vpc.hk.id
  cidr_block   = "172.16.1.0/24"
  zone_id      = "cn-hongkong-b"
  vswitch_name = "vsw-hk-a"
}
```

### 步驟 2：VPN 網關與 IPsec 隧道

每地 IDC 對應一個 VPN 網關，配置客戶網關（Customer Gateway，指向 IDC 側的公網出口 IP）與 IPsec 連接。

關鍵參數建議：

- **IKE 版本**：v2（協商更快、更穩定）
- **加密套件**：IKE 用 AES256 + SHA2-256 + DH group 14 或以上；ESP 用 AES256 + SHA2-256
- **DPD**：開啟，30s 探測，避免隧道僵死
- **路由模式**：優先用 **BGP 動態路由**，隧道震盪時路由自動收斂；若 IDC 側設備不支持 BGP，退而用靜態路由 + 健康檢查
- **高可用**：條件允許建雙隧道（主備或雙活），單條隧道故障時自動切換

阿里雲 CLI 建 IPsec 連接的核心思路：

```bash
# 1) 建 VPN 網關（綁定到 VPC/VSwitch）
aliyun vpc CreateVpnGateway --RegionId cn-hongkong \
  --VpcId vpc-xxx --VSwitchId vsw-xxx --Bandwidth 100

# 2) 建客戶網關（IDC 側公網 IP）
aliyun vpc CreateCustomerGateway --RegionId cn-hongkong \
  --IpAddress <澳門IDC出口公網IP>

# 3) 建 IPsec 連接
aliyun vpc CreateVpnConnection --RegionId cn-hongkong \
  --VpnGatewayId vpngw-xxx --CustomerGatewayId cgw-xxx \
  --IkeConfig '{"IkeVersion":"ikev2","IkeAuthAlg":"sha256","IkeEncAlg":"aes256"}' \
  --IpsecConfig '{"IpsecAuthAlg":"sha256","IpsecEncAlg":"aes256"}'
```

### 步驟 3：CEN 實例與 Transit Router

創建 CEN 企業版實例，在 cn-hongkong 與 cn-shenzhen 各創建 Transit Router，並將對應 VPC 作為「VPC 連接」掛載到 TR。

```bash
# 建 CEN 實例
aliyun cbn CreateCen --Name "cen-gba-crossborder"

# 掛載 cn-hongkong VPC 到 TR
aliyun cbn CreateTransitRouterVpcAttachment \
  --CenId cen-xxx --RegionId cn-hongkong \
  --VpcId vpc-hk-xxx --ZoneMappings.1.ZoneId cn-hongkong-b \
  --ZoneMappings.1.VSwitchId vsw-hk-a

# 掛載 cn-shenzhen VPC 到 TR（同理）
aliyun cbn CreateTransitRouterVpcAttachment \
  --CenId cen-xxx --RegionId cn-shenzhen \
  --VpcId vpc-sz-xxx --ZoneMappings.1.ZoneId cn-shenzhen-e \
  --ZoneMappings.1.VSwitchId vsw-sz-a
```

### 步驟 4：跨境帶寬包（重點，也是合規核心）

內地 ↔ 港澳屬於**跨境**互聯，CEN 默認不通，必須：

1. 購買**跨境帶寬包**（Bandwidth Package，跨境類型，互聯區域選「中國內地 ↔ 港澳」）。
2. 將帶寬包綁定到 CEN 實例。
3. 在兩個 TR 之間創建**跨地域連接（Peer Attachment）**，並分配帶寬。

```bash
# 購買並綁定跨境帶寬包
aliyun cbn CreateCenBandwidthPackage \
  --Bandwidth 100 --GeographicRegionA "China" --GeographicRegionB "China-HK" \
  --BandwidthPackageChargeType PREPAY
aliyun cbn AssociateCenBandwidthPackage --CenId cen-xxx --CenBandwidthPackageId cbwp-xxx

# 建跨地域連接並設帶寬
aliyun cbn CreateTransitRouterPeerAttachment \
  --CenId cen-xxx --TransitRouterId tr-hk-xxx --PeerTransitRouterId tr-sz-xxx \
  --CenBandwidthPackageId cbwp-xxx --Bandwidth 100
```

> ⚠️ **合規提示**：跨境帶寬包的購買與使用需要企業具備相應跨境資質，並遵守內地與港澳兩地的數據跨境監管要求。這一步在純內地組網裡完全不存在，是本架構最需要提前與客戶法務/合規團隊對齊的環節。

### 步驟 5：路由配置與回程對稱

- TR 路由表：確保 cn-hongkong TR 知道如何到達 10.20.0.0/16（珠海 IDC）與 172.17.0.0/16，反之亦然。
- VPN 側：IDC 側路由器要宣告雲上網段，雲側也要把 IDC 網段宣告回去。
- **回程路由對稱**：珠海 IDC 訪問澳門雲資源時，去程和回程路徑要對稱，否則會因單向路由被防火牆丟包（經典的「ping 得通一半」現象）。

## 五、合規與數據治理（澳門視角的核心價值）

這一段是本文與一般內地雲文章最大的差異化，也是澳門 Reseller 的專業壁壘所在。

**1. 跨境數據分級**
在設計階段就要和客戶一起把數據分級：哪些是可在 CEN 上自由流動的業務數據（如商品、訂單狀態），哪些是受限的個人資料（如會員身份、支付信息）。受限數據原則上**留在其產生地所在 Region**，不轻易跨境。

**2. 兩地法規的觸發點**
- 澳門 PDPA：個人資料的跨境傳輸需滿足目的地的保護水平或取得當事人同意。
- 內地《數據出境安全評估辦法》：達到規定數量門檻的個人資料 / 重要數據出境需申報安全評估。
- 架構層面的含義：**RDS、OSS 落在哪個 Region，就決定適用哪一套法律**。這是選型時的第一優先級考量，不是純粹的延遲或成本問題。

**3. 加密與審計**
- 傳輸層：IPsec 隧道 + CEN 骨幹本身加密。
- 存儲層：RDS/OSS 開啟 KMS 加密。
- 審計：開啟 CEN **FlowLog（流量日誌）** 與 VPC FlowLog，把跨境流量的五元組留痕，滿足合規審計與事後追溯。

## 六、實測與避坑清單

| 問題 | 現象 | 對策 |
|------|------|------|
| **MTU / MSS** | IPsec + CEN 疊加封裝後大包分片，TCP 連接卡頓 | 壓測後下調 MSS（建議 1350 左右），或調整 MTU |
| **跨境帶寬限速** | 實測吞吐遠低於預期 | 確認帶寬包峰值；跨境段帶寬是整條路徑瓶頸，按業務峰值留 30% 餘量 |
| **路由黑洞 / 不對稱路由** | 單向通、雙向不通 | 檢查 TR 路由表與 VPN 宣告，確保回程對稱 |
| **隧道僵死** | 一段時間後不通，重啟恢復 | 開啟 DPD + BGP 動態路由 |
| **延遲** | 跨境段延遲波動 | 澳門↔HK 通常個位數 ms，珠海↔深圳極低，主要延遲與抖動來自跨境段；對延遲敏感的業務就近落地 |
| **網段衝突** | CEN 建立後部分主機不通 | 前期規劃四段不重疊；已衝突則用 NAT |

高可用建議：VPN 雙隧道（主備或雙活）+ BGP 動態切換 + 兩 VPC 各跨兩個可用區，任一條鏈路或單個可用區故障時業務不中斷。

## 七、成本構成與優化

這套架構的月度成本主要由三部分構成：

1. **VPN 網關**：按帶寬規格計費（兩地各一個）。
2. **跨境帶寬包**：按帶寬峰值計費，是成本大頭，也是優化重點。
3. **CEN Transit Router**：按 TR 連接數與轉發流量計費。

省錢思路：

- 跨境帶寬包按**業務真實峰值**而非「越大越保險」購買，配合流量監控動態調整。
- 若兩地之間是大帶寬、低延遲、長期穩定的剛性需求，評估用**高速通道（物理專線）**替代 VPN + 跨境帶寬包，長期 TCO 可能更低。
- 雲上計算資源配合**預留實例 / Saving Plan**（見本系列後續「成本優化」篇）。

## 八、總結與適用場景

這套「雙 IDC + 雙 Region + CEN 跨境」架構，適合：

- 大灣區「一司兩地 / 多地」佈局、需要 IDC 與雲混合互訪的企業；
- 有雲上就近計算（數據中台、AI 推理）訴求，同時受跨境合規約束的場景；
- 未來計劃擴展到更多 Region（新加坡、其他海外節點）做全球組網的企業——CEN + TR 的中心化架構天然支持平滑擴展。

**核心記憶點**：跨境組網的技術不難，難在**跨境帶寬包的資質與合規**、以及**網段規劃與回程路由對稱**。把這兩點在設計階段就對齊，實施階段就能少踩八成的坑。
