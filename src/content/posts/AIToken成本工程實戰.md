# AI Token 成本工程實戰：把 LLM 賬單從黑盒變成可治理的賬本

> 關鍵詞：阿里雲、百煉、Higress、Token FinOps、ai-statistics、BssOpenApi、Batch、上下文緩存

## 一、為什麼 AI 賬單比雲賬單更難管

做過雲成本優化的人（見本系列成本優化篇）都習慣三件事：資源有 ID、用量有監控、賬單能對到實例。但 LLM 的賬單完全不是這個形態——**token 是一種流量型成本**：沒有資源實體可關停，消耗由 prompt 與對話長度驅動，同一個功能改一句 system prompt 成本就可能翻倍。

於是企業 AI 賬單普遍存在三個黑盒：

- **誰在花**：Key 共享、應用混用，賬單只有一個總數，無法落到部門；
- **花在哪**：客服、翻譯、OCR、Agent 混在同一個模型賬號下，場景占比全靠猜；
- **花得值不值**：沒有命中率、沒有單次對話成本，優化無從下手。

這篇記錄我們把 token 當作**一等成本對象**來治理的實踐：計量、歸因、預算、優化四個環節組成閉環，全部落在阿里雲生態內——百煉（Model Studio）出模型與平台計量，Higress AI Gateway 出請求級計量與控制點，BssOpenApi 出財務口徑的最終賬單。整體架構如下：三個計量源匯入成本賬本，歸因引擎產出告警、月報與台賬，優化動作再閉環下發到網關控制點與 Batch 調度。

## 二、計量層：三個數據源，各管一段

單一數據源永遠對不平 AI 賬單。我們用三個源互相校驗：

### 2.1 網關側：Higress ai-statistics（請求級、實時）

所有調用經網關時，`ai-statistics` 按 consumer 維度採集**輸入 token、輸出 token、緩存命中、延遲**指標。它是最細粒度、最即時的一層：能回答「哪個系統、哪條路由、哪個模型，這一分鐘花了多少 token」。兩個實測要點：流式（SSE）響應的用量在**流尾**才回傳，統計任務必須等流結束；超時截斷的請求要單獨標記，否則 token 會「憑空消失」。

### 2.2 平台側：百煉模型計量（折扣口徑）

平台計量是**折扣與計價規則的權威口徑**：輸入/輸出分開計價、Batch 與上下文緩存等折扣在這裡體現。官方文檔明確的兩條折扣規則值得寫進成本模型：

- **Batch（文件輸入，OpenAI 兼容）**：異步批量處理，所有成功請求的輸入與輸出 token 單價為對應模型實時推理價格的 **50%**；文件解析失敗、任務失敗、行級錯誤**不計費**；
- **顯式上下文緩存（Context Cache）**：對穩定復用的上下文（長 system prompt、工具列表、固定檢索塊）打緩存標記，**命中部分按標準輸入價的 10% 計費**（省 90%）；首次寫入緩存產生標準價 25% 的額外開銷——**至少命中一次才回本**。

### 2.3 賬單側：BssOpenApi（財務口徑、終版）

財務最終以賬單為準。用 `DescribeInstanceBill`（`IsBillingItem=true` 時返回 `ListPrice` / `Usage`）按賬期翻頁拉取計費項級明細：NextToken 分頁、`MaxResults` 上限 300、限流約 10 QPS；**最終賬單次月第 3 天 12:00 後可用**。這一層用來給前兩層「定錨」：網關與平台計量再細，月底必須與賬單對平。

### 2.4 三源勾稽：不平即告警

```
網關 Σ(consumer token)  ≈  平台 Σ(模型計量)  ≈  賬單 Σ(計費項金額 / 單價)
差額解釋項：Batch/緩存折扣 · 抹零與四捨五入 · 時區與賬期切線
```

這條等式借鑑了我們做 Reseller 對賬時的紀律（見對賬自動化篇）：**差額必須能被解釋，解釋不了就是數據問題，告警而不是帶病入庫**。金額與 token 全鏈路用定點數（Decimal）累加，禁用 float。

## 三、歸因：把 token 變成「誰的、哪個場景的」成本

計量解決「花了多少」，歸因解決「算誰的」。落地形態是一張事實表加兩張維表：

**事實表（每請求一行）**：時間、consumer、路由/應用、模型、輸入 token、輸出 token、緩存命中 token、請求 ID、場景標籤。

**維表一：consumer → 部門/場景負責人**。與對賬系統的「客戶 ↔ UID 歸組表」同一思路：新出現的 consumer 默認掛「待歸組」，**月度報表阻止出數**，逼著owner 先認領——歸因缺口比金額錯誤更難事後補。

**維表二：模型 → 單價版本表**。手工維護各模型輸入/輸出單價與生效區間，每月用賬單 `ListPrice` 回校一次；模型調價或活動變動時，歷史月份仍按當時版本單價復算，保證趨勢可比。

歸因產出三個視圖：**按部門**（預算責任）、**按場景**（客服/翻譯/OCR/Agent 的占比與單次成本）、**按模型檔位**（flash/plus/max 的流量分布——max 占比異常升高通常是路由失控的第一信號）。

## 四、預算與告警：先裝剎車再談花錢

預算分三層：公司月度總額 → 部門 → 場景。每層設軟閾值（提醒）與硬閾值（動作），動作不是「斷服務」而是**降級預案**：

| 信號 | 規則示例 | 自動動作 |
|------|----------|----------|
| run-rate 超預測 | 按日均外推月終 > 預算 110% | 通知 owner + 凍結新場景上線 |
| consumer 環比突增 | 某 consumer token 環比 > 3 倍 | 聯動 `ai-token-ratelimit` 臨時下調其配額 |
| 單請求異常 | 輸出 token 超 P99 基線 | 標記複查（多為 prompt 失控或死循環） |
| 緩存命中率下滑 | 命中率環比降 > 10pp | 檢查知識庫版本/緩存鍵失效 |

關鍵設計：**預算是「月」口徑，限流是「分鐘」口徑**，兩者靠 run-rate 換算聯動——月度預算剩餘除以期內分鐘數，就是當前的分鐘配額上限。硬閾值觸發時按預案順序降級：先暫停離線 Batch 任務（時效要求最低），再將分層路由整體下移一檔（max→plus、plus→flash），最後才限制非核心在線場景；核心客服鏈路始終保留配額。每次降級寫審計，恢復需 owner 確認。

## 五、優化閉環：五個槓桿按 ROI 排序

### 5.1 分層路由（數量級槓桿）

`qwen-flash` 做語言識別與意圖分類，`qwen-plus` 承接主對話，僅升級場景切 `qwen3-max`。實測這一步通常把 token 成本降一個數量級且體驗無感。歸因視圖裡「模型檔位分布」就是它的儀表盤。

### 5.2 兩層緩存，邊界分清

- **網關語義緩存（ai-cache）**：重複問題命中即不回源，**連模型 token 都不產生**；適合知識類高頻問答，邊界是帶個人上下文與多輪狀態的請求不進緩存；
- **平台顯式上下文緩存**：省的是**輸入 token 單價**（命中按 10% 計），適合長 system prompt、固定工具列表、穩定檢索塊；寫入有 25% 額外開銷，先估命中率再上。

兩層不互斥：語義緩存擋「重複問題」，上下文緩存擋「重複前綴」。

### 5.3 上下文工程

token 的大頭往往在輸入側：用 `ai-history` 做多輪裁剪、system prompt 瘦身、RAG 檢索頂替全文塞入、壓縮 Function Calling 的工具列表。每一項都直接反映在事實表的 input_tokens 列上。

### 5.4 時移與折扣

評測集回歸、批量質檢、報表生成等**離線任務全部走 Batch（50% 單價）**，失敗行不計費也意味著重試只花時間不花錢；生產固定模型快照版本，避免別名漂移導致行為變化後的隱性返工成本。

### 5.5 輸出治理

輸出 token 單價高於輸入：設 `max_tokens` 上限、用 `ai-json-response` 強制結構化減少廢話、合理 stop 序列。輸出/輸入 token 比值是輸出治理的儀表盤。

**每個槓桿上線前後各取 7 天計量做對比，差額寫入優化台賬**——優化不是口號，是要能拿出前後對照數的台賬條目。

## 六、一個月度節奏：把 FinOps 變成例行動作

| 時間 | 動作 | 產出 |
|------|------|------|
| 每月 1 日 | 網關計量封賬月表 | 請求級事實表月度快照 |
| 次月 3 日 12:00 後 | 拉 BssOpenApi 終版賬單 | 計費項明細 |
| 次月 4–7 日 | 三源勾稽 + 差額解釋 | 勾稽報告（不平即告警） |
| 次月 8 日 | 歸因月報發布 | 部門/場景/檔位三視圖 + 單價回校 |
| 次月 8 日當週 | 預算評審會 | 下月預算 + 優化清單（台賬驅動） |

8 號這個時點與對賬系統的調度一致：**等終版賬單，不等控制台緩存數據**。

## 七、避坑清單

| 坑 | 說明與對策 |
|----|-----------|
| 流式 token 在流尾 | 統計等流結束；超時截斷請求單獨標記，避免 token 憑空消失 |
| Batch 只計成功請求 | 失敗行免費但重試耗時；任務設計要冪等 |
| 顯式緩存寫入開銷 | 命中 < 1 次即虧；先估命中率再上，監控命中/寫入比 |
| 單價版本漂移 | 模型調價/活動變動：單價表帶生效區間，每月用賬單 ListPrice 回校 |
| 賬期與時區切線 | 勾稽以賬單 Billing Cycle 為準，不用網關本地月 |
| 語義緩存命中幻覺 | 命中 ≠ 正確：定期抽檢命中響應質量，知識更新帶版本號失效 |
| 歸因標籤缺口 | 新 consumer 掛「待歸組」並阻止月報出數，逼 owner 認領 |
| 國際站折扣機制差異 | Batch / 顯式緩存的開通範圍與價格以國際站控制台與模型列表為準，上線前實測 |
| 把優化當一次性項目 | 優化台賬 + 月度評審：沒有前後對照數的優化不算完成 |

## 八、總結

AI Token 成本工程沒有銀彈，只有一條鏈：**計量決定看不看得清，歸因決定算不算得準，預算決定剎不剎得住，優化決定省不省得下**。四段都落在現有組件上——Higress 出請求級計量與控制點，百煉出平台計量與折扣機制，BssOpenApi 出財務錨點——要補的只是中間那層薄薄的成本賬本與月度節奏。

雲賬單治理的是「資源」，AI 賬單治理的是「行為」：prompt、路由、緩存與輸出習慣。把行為變成可計量、可歸因、可預算的對象，LLM 賬單才會從每月一次的驚喜，變成每天看一眼的儀表盤。
