### 前言：那個每次都會遇到的老朋友

做過台灣或港澳地區專案的開發者，大概都對 Big5 編碼有著 PTSD 級別的記憶。

每次接手一個新專案，總會在意想不到的角落冒出亂碼：資料庫裡存的是 Big5，API 吐出來的是 UTF-8，前端拿到手之後 `é™³` 和 `æ˜Ž` 滿天飛。你以為轉個碼就好了，結果 `` 符號（Unicode Replacement Character）開始到處亂竄，告訴你有些字元在轉換的過程中已經永遠地消失了。

我最近連續做了幾個涉及舊系統的專案，每個都碰到了 Big5 的問題。最痛苦的不是問題本身，而是——我每次都要從頭跟 AI 助手解釋一遍什麼是 Big5、為什麼會出現亂碼、處理的時候要注意什麼。就像帶一個失憶的實習生，每次開新專案都要重新入職培訓。

直到我發現了 QoderWork 的 Skill 系統，這個死循環才終於被打破。

### 第一章：第一個專案裡的血淚教學

故事從一個資料遷移專案開始。客戶有一套運行了十幾年的 ERP 系統，資料庫用的是 Big5 編碼，現在要遷移到新的雲端架構，全面擁抱 UTF-8。聽起來很簡單對吧？「不就是 `iconv` 轉一下嗎？」如果你此刻心裡這樣想，恭喜你，你跟我當時一樣天真。

我打開 QoderWork，開始第一個專案的工作。起初，Qoder 對 Big5 的處理方式非常「教科書」：用 `iconv` 做編碼轉換，把 Big5 轉成 UTF-8。但實際情況遠比這複雜。

**第一個坑：Big5 不是只有一種 Big5**

標準的 Big5 只有一萬三千多個字，但現實世界中，台灣的作業系統和軟體早就把 Big5 擴展得面目全非。微軟的 CP950 在 Big5 的基礎上加入了日文假名和一堆符號；經濟部標準檢驗局的 Big5-2003 又塞了一批罕見字。你以為你在處理 Big5，其實你面對的是 CP950，而 `iconv -f big5` 根本不認識那些擴展字元。

我花了半個小時跟 Qoder 解釋：「不是，你不能只用 `big5`，你要用 `cp950`，或者用 `big5//TRANSLIT`，或者——算了，讓我寫一段程式碼給你看。」

**第二個坑：轉碼失敗的無聲殺手**

`iconv` 預設的行為是遇到無法轉換的字元就報錯。但如果你在程式碼裡加了 `@iconv_open` 或者用了 `//IGNORE` 參數，它會默默地把問題字元丟掉，繼續執行。結果就是你遷移了一百萬筆資料，看起來都成功了，直到三個月後客戶打來說：「我客戶的名字怎麼少了兩個字？」

這個問題我反覆叮囑了 Qoder 好幾次：「轉碼之後一定要驗證字串長度！如果轉換後的字串突然變短了，一定是有字元被丟掉了，不要當沒事繼續跑。」

**第三個坑：混合編碼的混沌**

舊系統最怕的不是純 Big5，而是 Big5 和 UTF-8 混雜在一起的狀態。可能是某次升級只轉了一半，可能是某個欄位被手動塞了不同編碼的資料。你對整張表做 `iconv -f big5 -t utf-8`，結果那些本來就是 UTF-8 的資料被二度轉碼，變成了誰都看不懂的火星文。

我教 Qoder 寫了一個偵測函式：在轉碼之前先判斷每個字串的實際編碼，只有確認是 Big5 的才做轉換，已經是 UTF-8 的就放過它。聽起來很基本的防護，但 AI 在沒有上下文的情況下，真的不會主動想到。

### 第二章：當 AI 終於「學會」了

經過大約兩天的反覆指導，Qoder 終於把 Big5 的處理流程摸熟了。它學會了在轉碼前先做編碼偵測（用 `mb_detect_encoding` 搭配 strict mode），學會了用 `//TRANSLIT` 而不是 `//IGNORE`，學會了在轉換後比對字串長度和抽樣驗證，甚至學會了在遇到無法確定的字元時主動問我而不是自作主張。

那幾天寫出來的程式碼品質很不錯，遷移腳本跑得也很穩定。我甚至有點感動——終於有一個「助手」能完整地理解 Big5 處理的所有眉角了。

然後，第二個專案來了。

同樣是舊系統，同樣有 Big5 問題。我開了一個新的 QoderWork session，開始描述需求。Qoder 的回覆是：

> 「好的，我們可以用 `iconv` 將 Big5 編碼轉換為 UTF-8，以下是一個簡單的範例⋯⋯」

我盯著螢幕，有一種強烈的 déjà vu。那個失憶的實習生又回來了。

### 第三章：原來可以這樣——發現 Skill 系統

就在我準備重新開始漫長的教學過程時，我想起了 QoderWork 有一個 Skill 系統。之前我只是隱約知道它的存在，知道它可以把一些「最佳實踐」保存下來，但從來沒有認真研究過。

那一刻我突然意識到：這不就是我需要的嗎？

我把 Big5 的處理方式想成一個「技能」——它有一套明確的流程、有特定的踩坑注意事項、有驗證步驟。如果我能把這些知識寫成一個 Skill，那以後每次開新專案，Qoder 就能自動載入這些知識，不用我重新教。

於是我做了一個實驗。

**建立 Skill 的過程**

我直接跟 QoderWork 說：「幫我把剛才處理 Big5 的方式整理成一個 skill。」

它調用了 `create-skill` 的流程，引導我一步步把知識結構化。最終生成的 SKILL.md 大致長這樣（簡化版）：

```markdown

  Big5 編碼的場景。

---

# Big5 編碼處理指南

## 核心原則
- 永遠先偵測編碼，再做轉換
- 使用 //TRANSLIT 而非 //IGNORE
- 轉換後必須驗證，不能假設成功

## 編碼偵測
在轉換前，對每個字串做編碼偵測：
1. 使用 mb_detect_encoding 搭配 strict mode
2. 偵測順序：UTF-8 → Big5/CP950 → ISO-8859-1
3. 如果無法確定編碼，標記為 unknown 並人工確認

## 安全轉碼流程
1. 使用 iconv 或 mb_convert_encoding
2. 優先使用 cp950 而非 big5 作為 source encoding
3. 加上 //TRANSLIT 處理無法精確對應的字元
4. 絕對不要用 //IGNORE，它會無聲地丟掉字元

## 混合編碼處理
- 逐筆、逐欄位偵測編碼，不要整批處理
- 已經是 UTF-8 的資料跳過轉換
- 記錄每一筆的轉換狀態，方便事後排查

## 驗證步驟
- 轉碼後比對字串長度（異常縮短 = 有字元丟失）
- 抽樣比對轉換前後的中文字是否可讀
- 特別注意人名、地名中的罕見字
- 生成轉換報告：成功數、失敗數、跳過數

## 常見踩坑點
- Big5 ≠ CP950，Windows 系統大多是 CP950
- 倚天中文系統的擴展字元不在標準 Big5 範圍內
- 日文假名在 CP950 中有，但在標準 Big5 中沒有
- 全形空格（0xA1 0x40）在部分工具中會被誤判
```

這個 Skill 被存放在 `~/.qoderwork/skills/big5-handling/SKILL.md`，成為 QoderWork 全域知識庫的一部分。

### 第四章：第二個專案的實戰驗證

建立 Skill 之後，我開了第二個專案的 session。這次的任務是串接一個台灣政府單位的舊 API，回傳的資料是 Big5 編碼的 XML。

我剛在對話中提到「Big5」這個關鍵字，Qoder 就自動載入了我之前建立的 skill。它的回覆風格完全不一樣了：

之前要花兩天教學的東西，現在零成本就能用了。

### 第五章：Big5 處理的技術深潛

既然這篇文章是給開發者看的，讓我多分享一些在實際專案中累積的技術細節。這些都是教科書上不會寫、但踩過坑才知道的東西。

**偵測編碼的正確姿勢**

很多人用 `mb_detect_encoding` 的時候不設 strict mode，結果它會給你一個「猜測」而不是「判斷」。在 Big5 的場景下，一個 UTF-8 的中文字串在非 strict mode 下有高達 30% 的機率被誤判為 Big5。正確的做法是：

```php
$encoding = mb_detect_encoding($string, ['UTF-8', 'BIG-5', 'CP950', 'ISO-8859-1'], true);
```

第三個參數 `true` 就是 strict mode，開啟後只有字串完全符合某個編碼的規則才會回傳該編碼。如果都不符合，會回傳 `false`，而不是給你一個不靠譜的猜測。

**CP950 vs Big5 的選擇**

在絕大多數的台灣舊系統場景下，你面對的其實都是 CP950 而不是標準 Big5。CP950 是微軟對 Big5 的擴展，多出了大約四百多個字元，包括日文假名（這是當年為了支援台日混排加進去的）和一些特殊符號。如果你在 `iconv` 裡用 `big5` 當 source encoding，碰到這些擴展字元就會報錯。所以我的經驗法則是：永遠用 `cp950` 當 source encoding，除非你 100% 確定資料來源使用的是標準 Big5。

**轉碼的容錯策略**

`iconv` 提供了兩個容錯後綴：`//TRANSLIT` 和 `//IGNORE`。前者會嘗試用相似的字符替代無法精確轉換的字元（比如全形變半形），後者會直接丟掉無法轉換的字元。

在我的實際經驗中，`//TRANSLIT` 是唯一的選擇。`//IGNORE` 造成的資料丟失是靜默的，你不會收到任何警告，字就這樣消失了。而 `//TRANSLIT` 至少會保留一個「近似」的字元，讓你知道這裡原本有東西。

不過要注意，`//TRANSLIT` 的行為依賴系統的 `libc` 實現，在不同作業系統上可能有細微差異。如果你的腳本要在 Linux 和 macOS 之間切換，建議先跑一組測試資料確認行為一致。

**Node.js 環境下的替代方案**

如果你的專案是 Node.js 技術棧，`iconv` 的綁定有時會讓人頭痛（特別是編譯 native module 的部分）。這時候可以考慮用 `iconv-lite`，它是純 JavaScript 實現，不需要編譯，而且對 Big5 和 CP950 的支援都很到位。不過要注意，`iconv-lite` 不支援 `//TRANSLIT`，遇到無法轉換的字元會預設替換為 `?`。你需要自己加一層錯誤處理：

```javascript
const iconv = require('iconv-lite');

function safeConvert(buffer) {
  // 先偵測編碼
  if (iconv.encodingExists('cp950')) {
    try {
      const decoded = iconv.decode(buffer, 'cp950');
      // 檢查是否有替換字元（? 或 U+FFFD）
      if (decoded.includes('\ufffd') || decoded.includes('?')) {
        console.warn('轉碼過程中可能有字元丟失，請人工確認');
      }
      return decoded;
    } catch (e) {
      console.error('轉碼失敗:', e.message);
      return null;
    }
  }
}
```

**Python 環境的注意事項**

Python 3 的 `str` 預設就是 Unicode，所以 Big5 的問題通常出現在讀取外部資料的時候。`bytes.decode('big5')` 在遇到 CP950 擴展字元時會拋出 `UnicodeDecodeError`。建議用 `errors='replace'` 搭配日誌記錄：

```python
def decode_big5_safely(data: bytes) -> str:
    try:
        # 先嘗試 cp950（包含擴展字元）
        return data.decode('cp950')
    except UnicodeDecodeError:
        # 回退到 big5，用 replace 處理並記錄問題
        decoded = data.decode('big5', errors='replace')
        replacement_count = decoded.count('\ufffd')
        if replacement_count > 0:
            logger.warning(f'有 {replacement_count} 個字元無法正確解碼')
        return decoded
```

### 第六章：Skill 系統帶來的更多可能

Big5 只是第一個被我沉淀成 Skill 的知識。在體驗到它的好處之後，我開始審視自己日常工作中還有哪些「每個專案都會碰到、每次都要重新教 AI」的知識。

我陸續又建了幾個 Skill，比如：處理台灣身分證字號的驗證邏輯（要考慮新旧格式和外籍人士的特殊編號規則）、台灣地址的解析和標準化（從「台北市信義區信義路五段七號」到結構化的縣市/區域/路段資料），以及跟台灣金流 API 串接時的常見注意事項。

每一個 Skill 的建立過程都是一樣的：先在一個專案裡跟 Qoder 反覆磨合，直到處理方式穩定可靠，然後讓 Qoder 把這些知識整理成 SKILL.md。下一次開新專案的時候，這些知識就會自動成為 Qoder 的背景知識的一部分。

這種模式改變了我跟 AI 助手的協作方式。以前是「每個專案從零開始教」，現在是「在第一個專案裡認真教，之後的專案直接享受成果」。AI 不再是那個每天失憶的實習生，而是一個能累積經驗的團隊成員。

### 結語：知識不該跟著專案結束而消失

作為開發者，我們每天都在解決問題，每天都在累積經驗。但這些經驗往往只存在於我們的腦子裡，或者散落在各個專案的 commit message 和 TODO 註解中。下一次碰到同樣的問題，我們還是得重新想一遍、試一遍。

Skill 系統給了我一個啟發：AI 時代的知識管理，不應該只是把文件丟進 wiki，而是應該把「可執行的經驗」結構化，讓它能在需要的時候自動出現。

如果你也有類似的經驗——某些技術問題你已經解決過無數次，每次換專案卻還是要重頭來過——不妨試試看把你的解決方案變成一個 Skill。花二十分鐘整理一次，省下的是未來無數次重複教學的時間。

那個失憶的實習生，其實可以不再失憶。關鍵在於你願不願意花一點時間，把經驗好好寫下來給它。
